## SDD explore: book-venue-closes (reconciliation slice 2)

2026-09-23. HEAD `3fec07a`. Investigates auto-booking `ATTRIBUTABLE_SINGLE_ALLOCATION`/`ATTRIBUTABLE_FULL_CLOSE` verdicts from `reconciliation.scan` (slice 1, shipped) into `ledger_entries`/`execution_attempts`, per [[sdd-propose-detect-venue-originated-position-changes]]'s "Out, next change" scope.

### WHAT THE PROPOSAL ASSUMED IS DONE vs WHAT ACTUALLY LANDED

Migration `0021_execution_attempts_live_close.py` shipped for `open-position-safely`, NOT for this slice, and it does something DIFFERENT from what the proposal/explore predicted:
- Predicted: drop the unconditional UNIQUE, replace with `origin`-scoped partial unique `WHERE origin = 'SYSTEM'`, add `execution_attempts.origin` column.
- Actual (`0021`, `execution/infrastructure/models.py:33-45`): drops the UNIQUE, replaces with a STATUS-scoped partial unique `ux_execution_attempts_live_close ... WHERE closes_allocation_id IS NOT NULL AND status = 'SUBMITTED'`, plus a plain `ix_execution_attempts_closes_allocation`. No `origin` column anywhere — confirmed via `grep -r "origin"` across `backend/src` returning zero matches for this concept.
- Consequence: this accidentally already satisfies book-venue-closes' need for "many VENUE-origin closes per allocation", because a venue-booked row would be constructed directly as `status='FILLED'` and the partial index only constrains `SUBMITTED` rows. No new migration is needed for THAT purpose. But the `origin` discriminator itself (SYSTEM vs VENUE, for auditability/filtering/future UI) is entirely unbuilt — genuinely slice-2 work.

### Q1 — Current state end to end, attach point

`reconciliation.scan` flow: `ReconciliationScanHandler.handle` (`reconciliation/application/reconciliation_scan_handler.py:110-132`) — DRY_RUN hard skip, else calls `ScanPools.scan(job.id)` (`scan_pools.py:98-145`), then unconditionally enqueues its successor. `ScanPools._scan_pool` (`scan_pools.py:147-247`) compares venue vs ledger per market-keyed symbol (`market_key()`, `application/market_key.py`), calls the pure `classify()` ladder (`domain/classify.py:18-92`), computes `next_consecutive_scans`/`derive_status` (`domain/discrepancy.py:53-86`), and calls `DiscrepancyRepositoryPort.upsert_open` (`ports.py:161-182`) — this is the ONLY write in slice 1, into `reconciliation_discrepancies` (migration `0020`). A row is `CONFIRMED` once `consecutive_scans >= reconciliation_confirmations` (default 2, `shared/config.py:281`); scan interval default 30s (`shared/config.py:274`, live-measured per `[[reconciliation-interval-measured-30s-chosen]]`).

**Attach point for booking**: right where `status` transitions to `CONFIRMED` for kinds `ATTRIBUTABLE_SINGLE_ALLOCATION`/`ATTRIBUTABLE_FULL_CLOSE`, inside or immediately after `_scan_pool`'s `upsert_open` call (`scan_pools.py:227-239`), OR as a separate use case sweeping still-open `CONFIRMED` rows of those two kinds. The table currently has NO field marking "already booked" — `status` only tracks OBSERVED/CONFIRMED, and a row stays CONFIRMED on every subsequent scan until it resolves. Without a booked marker, a naive attach at "status == CONFIRMED" re-attempts booking on every scan after the first. The `UNIQUE (exchange, venue, exchange_fill_id)` on `ledger_entries` (`ux_ledger_exchange_fill`, migration `0019:65-68`, columns `exchange,venue,exchange_fill_id`) makes a re-attempt safe from double-recording the SAME fill, but re-fetching fills every 30s for a still-open CONFIRMED row is wasteful and each attempt still needs to construct a fresh, uniquely-ided `execution_attempts` row (see Q2) even when it inserts zero new ledger rows.

### Q2 — What booking must write, and constraint collisions

Confirmed `ledger_entries` constraints exactly as CLAUDE.md states (migration `0005_ledger_execution.py:92-133`): `strategy_id`/`allocation_id`/`execution_attempt_id` NOT NULL with FKs, append-only via `trg_ledger_no_truncate`/`trg_ledger_no_update_delete`, `UNIQUE(exchange, venue, exchange_fill_id)`.

`execution_attempts` (`execution/infrastructure/models.py:20-90`): `ck_execution_attempts_one_origin` (0012) still `(reservation_id IS NOT NULL) <> (closes_allocation_id IS NOT NULL)` — a venue-close row sets `closes_allocation_id`, leaves `reservation_id` NULL, satisfies this cleanly, no collision. BUT:
- `client_order_id: Text NOT NULL UNIQUE` (`models.py:82`) — a venue-originated close was never submitted by this system, so it has no client-chosen order id. Booking MUST synthesize one (e.g. a fresh `uuid4()`, or a deterministic id derived from the venue's own `exchange_order_id`/`exec_id`) to satisfy NOT NULL+UNIQUE. **Neither the proposal nor the prior explore flagged this** — it is new evidence from this pass.
- `status` CHECK (`ck_execution_attempts_status`, 0005) allows `'FILLED'` directly — constructing the attempt already-FILLED needs no `SUBMITTED` transition, confirming the earlier explore's recommendation.
- `quantity`/`quote_amount` one-of CHECK (`ck_execution_attempts_one_size`, 0011) — a close is sized in base (`quantity`), matching `ClosePosition`'s own convention.
- `leverage` nullable (0015) — fine to leave null or populate from a live read; not required by any CHECK.
- The partial unique `ux_execution_attempts_live_close` (0021) only restricts `SUBMITTED` rows — no collision for a directly-FILLED venue row, confirmed above.
- `RecordFill`/`FillRecord` (`ledger/application/record_fill.py:1-47`, `execution/application/ports.py`) is directly reusable: it maps `FillRecord` → `LedgerEntry` and calls `LedgerRepositoryPort.insert`. `SettleExecution._record` (`execution/application/settle_execution.py:155-193`) is the exact template to mirror, including resolving `usd_rate` via the existing `UsdRateProviderPort` (line 39, 69, 114) — CLAUDE.md rule 7 (rate recorded at fill time, never backfilled) applies identically to a venue-originated fill.
- `origin` column: does not exist (see above). Needed if SYSTEM vs VENUE provenance must be queryable later (audit, future UI, a rule like "never let CloseOrphans act on a VENUE-booked residual"); its absence is not a correctness blocker for booking one fill, only a debt if omitted.

### Q3 — Venue API for the fill fetch

Both adapters currently expose only an ORDER-scoped fetch, confirmed unmissable in code — no symbol+time-window variant exists yet, matching the prior explore's "Missing" finding exactly:
- Bybit: `BybitTradeClient.fills_for(order_link_id)` (`shared/infrastructure/bybit/trade_client.py:216-226`) calls `GET /v5/execution/list` (`EXECUTIONS_PATH`, line 49) with `{"category": "linear", "orderLinkId": ...}` only. `_parse_execution` (line ~308-320) maps `execId`→`exec_id` (this is what must become `exchange_fill_id`), `orderId`, `execPrice`, `execQty`, `execFee`, `feeCurrency`, `execTime` (ms). A symbol+window variant needs new params `symbol`+`startTime`+`endTime` (undocumented in this codebase yet — CLAUDE.md's 2026-08-27 round-trip note names `execQty`/`execPrice`/`execFee`/`feeCurrency`/`execTime`/`execId`/`orderId` as confirmed-live fields, and flags `closedSize`/`execFeeV2` as present in the raw payload but unparsed here). Pagination/time-window limits for `/v5/execution/list` are UNVERIFIED in this repo — would need a live probe, exactly as the prior explore already flagged for the position-snapshot endpoint.
- Binance: `BinanceTradeClient.order_id_for` + `.fills_for(symbol, order_id)` (`shared/infrastructure/binance/trade_client.py:287-337`) call `GET /fapi/v1/userTrades` (`USER_TRADES_PATH`, line 62) with `{"symbol": ..., "orderId": ...}` only. `_parse_execution` maps `id`→`trade_id` (→ `exchange_fill_id`), `orderId`, `price`, `qty`, `commission`, `commissionAsset`, `time` (ms). CLAUDE.md's own doc comment at line 10-12 of this file already states `/fapi/v1/userTrades` "accepts `symbol` and a [time range]" for the general endpoint, but the client only wires the `orderId`-scoped call — the symbol+window call is unimplemented, not unavailable. Binance's public docs (outside this repo, unverified live here) describe `startTime`/`endTime` with a documented 7-day window and 3-month history depth, matching the prior explore's citation; a live probe should confirm current rate-limit weight before fixing a fetch interval.
- Both `Fill` (`execution/domain/fill.py`) and the raw `*Execution` dataclasses already carry every field a `FillRecord` needs (`exchange_order_id`, `exchange_fill_id`, `quantity`, `price`, `fee`, `fee_currency`, `filled_at`) — the new fetch method only needs a new client method + a new adapter method, not new domain types.

### Q4 — Attribution safety and the PnL-if-wrong question

`classify()`'s ladder (`domain/classify.py:71-92`) makes `ATTRIBUTABLE_SINGLE_ALLOCATION`/`ATTRIBUTABLE_FULL_CLOSE` safe specifically because both require the venue to report a net position consistent with EXACTLY the allocations the ledger already tracks as open on that market — one-way (BUYSELL) mode means the venue holds one net figure per symbol, so a flat venue (rung 2, `ATTRIBUTABLE_FULL_CLOSE`) or a single open allocation disagreeing (rung 3, `ATTRIBUTABLE_SINGLE_ALLOCATION`) leaves no room for which allocation moved to be ambiguous — there is only one candidate. `AMBIGUOUS_PARTIAL_REDUCE` (rung 4, two+ open allocations) is unbookable because size alone cannot say which allocation the venue's partial reduce came from — any FIFO/LIFO/pro-rata split would be invented, not observed (explore #181's own words, still true). `NO_MATCHING_ALLOCATION` (rung 1) is unbookable because there is no allocation, strategy or reservation to attribute the fill to at all — fabricating one violates `ledger_entries`' NOT NULL FKs and rule 6.

**If attribution is WRONG anyway** (e.g. classify() itself has a bug, or a race lets the wrong allocation be picked — see Q5): the ledger is append-only (`fn_ledger_append_only`, migration `0005`, `trg_ledger_no_update_delete`/`trg_ledger_no_truncate`) — a wrongly-attributed row can NEVER be edited or deleted, only offset by a NEW compensating entry, if the domain even supports one (it currently does not — every ledger row assumes a real fill happened). A wrong booking corrupts that strategy's PnL permanently unless a manual correcting entry mechanism is designed in, and corrupts the OTHER strategy's PnL too if the fill actually belonged to a different strategy sharing the symbol — this is NOT a capital-safety bug (rule 4/`available` stays a live venue read, per explore #181), it is a silent, permanent accounting corruption. This is the single highest-severity risk of slice 2 and argues for either (a) a strict two-scan CONFIRMED requirement already in place, or (b) an additional guard (e.g. requiring `open_allocation_ids` unchanged between the confirming scan and the booking attempt) before any write — undecided, flagged for design.

### Q5 — Interaction with open-position-safely (shipped: `holding_guard.py`, `close_orphans.py`, `holding.py`, `open_after_close.py`)

Once a venue close is booked, the strategy's `net_base` on that symbol goes to zero (the booked fill's quantity exactly closes what `ATTRIBUTABLE_SINGLE_ALLOCATION`/`_FULL_CLOSE` already proved matched). `HoldingGuard.check` (`signals/application/holding_guard.py:109-129`) then reads `strategy_net(holdings, strategy_id) == 0` (`domain/holding.py:83-97`) and returns `proceed=True` immediately (`holding_guard.py:126-127`) — it never reaches `_classify_divergence` at all. **This is a strict improvement, not a regression**: before booking, that same symbol would have been GHOST (venue flat, strategy ledger still open) — refused with a WARNING (`holding_guard.py:192-199`) — every single time a signal arrived, forever, until a human intervened. After booking, GHOST for that specific close never recurs. REAL and AMBIGUOUS are unaffected for symbols the scan has NOT (yet, or ever) confirmed as attributable — the guard's classification (`classify_orphan`, `domain/holding.py:51-80`) is entirely independent of `reconciliation_discrepancies`; it does its own live venue read (`VenueNetPositionPort`) at guard time, never consults the discrepancy table.

**Race**: `HoldingGuard._classify_divergence` (`holding_guard.py:163-199`) makes its OWN live venue read at guard time, so it is not vulnerable to a STALE discrepancy row — even if reconciliation's booking transaction is mid-flight, the guard's classification reflects whatever the venue currently reports, not what the scan last observed. The narrower race is INSIDE booking itself: reconciliation's scan interval (30s) is uncoordinated with `HoldingGuard`'s in-flight check (`InFlightWorkPort.in_flight`, `holding_guard.py:121-122`) and with `CloseOrphans` — nothing in `ScanPools`/booking takes the pool's advisory lock (`_lock.acquire`, referenced in design #207) that `AllocateCapital`/`ClosePosition` use, and nothing in the guard/close path currently checks whether reconciliation has a booking in flight for the SAME allocation. Concretely: if `CloseOrphans` (REAL-orphan path, `close_orphans.py:153-247`) places a SYSTEM-origin close on an allocation in the SAME window reconciliation is trying to book a VENUE-origin close for the SAME fill event, only the `UNIQUE(exchange,venue,exchange_fill_id)` constraint on `ledger_entries` stops a double-record — whichever insert loses gets a database error, and slice 2's booking use case needs to treat that specific IntegrityError as an expected, swallowed outcome (a benign "someone else already recorded this fill"), not a hard failure. No code currently handles this; it is new work, not yet designed.

### Q6 — Genuinely undecided, belongs to the owner

1. **Booking cadence / "already booked" tracking** — the discrepancy table has no field marking a row already acted on; whether to add one (and its shape) is a schema decision, not a designer inference.
2. **Correction mechanism for a wrong attribution** — the ledger is append-only and has no compensating-entry concept today; whether slice 2 ships one, or accepts the corruption risk as-is pending manual DB intervention, is an owner risk-tolerance call (Q4).
3. **`origin` column** — build it now for audit/future-rule value, or defer since nothing currently requires it functionally (the 0021 partial index already accidentally provides the uniqueness slice 2 needs without it)?
4. **synthesized `client_order_id`** — what scheme (fresh uuid4 vs derived from venue id) is a naming convention decision with no functional stakes either way, but should be consistent with how `exchange_order_id`/`exchange_fill_id` are read back for debugging.
5. **Fill-fetch interval / rate-limit budget** — both venues' symbol+window endpoints are unimplemented and their live rate-limit weight is unverified in this repo; needs the same live-measurement work unit the interval-30s decision already used for the position-snapshot endpoint.
6. **Whether booking takes the pool's advisory lock** — doing so would serialize it against `AllocateCapital`/`ClosePosition` and remove the Q5 race outright, at the cost of a reconciliation-side use case newly depending on `allocation`'s lock primitive across a module boundary that currently does not exist.
