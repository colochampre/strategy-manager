## SDD explore: operator-panel

2026-09-24. HEAD `a7f3297`. Investigates the frontend/panel change per the owner's nine binding decisions (Engram `project/frontend-decisions` #260) and prior facts (`project/frontend-serving-and-design` #254). Read-only pass; no code changed.

### 1. Strategy-return curve (decision 6, option A)

**`reservations.amount` (= `AllocationResult.granted`) IS ALREADY the per-trade capital denominator — no new column is required for it.** Traced `AllocateCapital.allocate` (`allocation/application/allocate_capital.py:97-174`): `requested = Money(amount=requested_from_percent(pool_balance.total, policy.allocation_percent), currency=...)` is built in `process_signal.py:510-513` from `pool_balance.total` (the live pool balance at that instant, from `PoolBalanceAdapter`/`DbBalanceSource`) × `allocation_percent`. `decide()` (`allocation/domain/decision.py:37-73`) caps it at pool availability and returns `granted`; `AllocateCapital` persists `granted` as `reservations.amount` (`allocate_capital.py:160`). Per CLAUDE.md's futures section, `granted` is MARGIN, and `size = granted * leverage / price` is what actually gets ordered — so `reservations.amount` is literally "capital placed at risk for this trade," independent of the account's total balance or any deposit/withdrawal that happened before or after. A return computed as `realized_pnl_for_allocation / reservations.amount` is deposit/withdrawal-agnostic by construction and needs zero schema change to start recording it going forward.

Caveat found: recovering the ORIGINAL `requested` (hence the pool balance at that instant) from `granted` alone only works for `DecisionOutcome.FULL` (`granted == requested`); for `PARTIAL` outcomes `granted < requested` and the original pool-balance-at-request-time is not recoverable after the fact. This does not block the `granted`-denominator approach (it never needed `requested`), but it does mean a *pool-balance equity curve* (option not chosen, listed for contrast) is NOT derivable retroactively and would need a new snapshot-history table — `pool_balance_snapshots` (`accounts/infrastructure/balance_snapshot_repository.py`) keeps ONLY the latest row per pool (confirmed by its `ON CONFLICT DO UPDATE` upsert, no history).

**PnL per closed allocation from `ledger_entries`, confirmed derivable**: opening AND closing fills carry the SAME `allocation_id`. Traced `ClosePosition.close` (`execution/application/close_position.py:67-72`): `CloseCommand.allocation_id` is documented as "the reservation that OPENED the position being closed — the same id the opening fills carry." `SettleExecution._record` (`settle_execution.py:155-193`) writes every fill (open or close) through `FillRecord(allocation_id=attempt.allocation_id, ...)` into `ledger_entries` (`ledger/infrastructure/models.py`), which is append-only (rule 6, triggers from migration 0005) and carries `symbol`, `side`, `quantity`, `price`, `fee`, `fee_currency`, `notional`, `filled_at`, `usd_rate_at_fill` per fill. A closed allocation's realized PnL in native settlement currency is therefore `SUM(sell notional) - SUM(buy notional) - SUM(fee, converted to settlement ccy when fee_currency differs)`, grouped by `allocation_id`, computable once the position nets to zero. **No existing read method does this aggregation yet** — `ReadHeldBase` (`ledger/application/read_held_base.py`, used by `ClosePosition`) answers "what base currency does this allocation hold now," and `ReadSymbolPositions`/`SqlAlchemyLedgerRepository.net_positions_by_symbol` (`ledger/infrastructure/repository.py`) answers "what does a whole pool hold by symbol" — both are net-quantity projections, not PnL projections. A new read model (e.g. `ReadRealizedPnlByAllocation`) is genuinely new application-layer work, though it can reuse the same repository/session pattern.

The ledger is confirmed EMPTY under DRY_RUN (per the task brief and consistent with `FakeExchangeAdapter` never hitting a real venue) — so this whole curve renders on zero data until `DRY_RUN=false` and the first real trades land; it needs to degrade gracefully (empty state), not assume data exists.

Design-phase decision, not resolved here: whether "return %" compounds per-trade (chain of `1 + pnl/granted` factors, a proper equity-curve-of-returns) or is shown as a flat per-trade list plus a separately-computed running total; and whether fee-currency conversion (when `fee_currency != settlement_currency`, e.g., a base-currency fee) needs its own USD-rate-style handling or can be ignored as immaterial. `usd_rate_at_fill` exists per entry, so a fee mismatch is technically convertible, but nothing in the codebase does this today.

### 2. Allowed pairs (decision 1)

No existing "allowed pairs" or per-strategy symbol allowlist concept anywhere in the codebase (confirmed: `Strategy`/`AllocationPolicy`, `strategies.infrastructure.models.StrategyRow`, `StrategyPolicySnapshot` carry no symbol/pairs field). `symbol` arrives per-signal from TradingView's raw `{{ticker}}` (`signals/domain/alert.py:39,54`), never validated against a strategy-level allowlist.

**Normalization already exists and is reusable**: `execution.domain.market_symbol.market_spellings(symbol)` (`market_symbol.py:65-82`) returns every spelling a market can wear (bare + `.P` + `_PERP`), and `reconciliation.application.market_key.market_key(symbol)` (`market_key.py:18-20`) reduces a symbol to one canonical upper-cased bare form (`strip_contract_marker(symbol).upper()`). An allowed-pairs check should store pairs in `market_key()`'s canonical form and compare `market_key(context.symbol)` against the stored set — this avoids re-inventing normalization and stays consistent with how reconciliation already compares markets.

**Attach point**: `ProcessSignalHandler.handle()` (`signals/application/process_signal.py:322-332`) already has a cheap pre-lock guard pattern immediately after loading `policy`: `if (policy.exchange, policy.venue) not in self._tradable_pools: return self._refuse_untradable_pool(...)`. An allowed-pairs check belongs right there, before `_handle_consumes`/`_handle_releases` — same shape, same refusal style (a named refusal method, WARNING-level per decision 1 "unlisted pairs refused with WARNING"). `StrategyPolicySnapshot` (`allocation/application/ports.py:20-32`) would need an `allowed_pairs` field (or the check reads it through a separate port) to reach `process_signal.py` from wherever it is stored.

**Storage shape — real trade-off, design decision**:
- *Array column* (`strategies.allowed_pairs TEXT[]`): one migration, no join, trivial to read alongside the rest of the policy in one query (matches how `StrategyPolicySnapshot` is already assembled as one flat read). Con: no per-row metadata if the owner ever wants per-pair settings later (e.g. a per-pair allocation cap), and Postgres array `CHECK`/uniqueness constraints are clunkier than a table's.
- *Child table* (`strategy_allowed_pairs(strategy_id, symbol)`): normal CRUD shape (`INSERT`/`DELETE` per pair from Settings UI), a natural place to hang audit columns later, standard FK/UNIQUE. Con: one more join into the hot path (`policy_for`) that currently reads `strategies` alone via `SqlAlchemyStrategyRepository`.

Note that "stats by pair" (decision 1) does NOT need the allowed-pairs table at all — `ledger_entries.symbol` already carries the traded symbol per fill, so per-pair PnL/trade-count is a `GROUP BY symbol` over the ledger, independent of whatever the allowed-pairs list currently says (a pair could be removed from the allowlist after trades already happened on it, and those historical stats must still show).

### 3. Enable/disable event log (decision 9) and archive (decision 1)

**Current PATCH path**: `UpdateStrategy.update()` (`strategies/application/update_strategy.py:74-99`) reads the current `Strategy`, applies `replace()` for whichever of `name`/`fill_mode`/`allocation_percent`/`enabled` was sent, writes it back, commits. No event/history table exists — `enabled` is a bare boolean on `strategies` (`infrastructure/models.py:46-48`), no `updated_at` trail per field, nothing records WHEN it flipped or for how long. An enable/disable event log is entirely new: a new table (e.g. `strategy_enable_events(strategy_id, enabled, at)`) written inside the same `UpdateStrategy.update()` transaction whenever `command.enabled is not None` and differs from the current value — cheap to add since the use case already has `commit` and the old/new `Strategy` in hand.

Cumulative uptime (decision 9) is then a derived read: sum of `(disabled_at - enabled_at)` intervals from that event log, plus the still-open interval if currently enabled — a query, not a stored running total (avoids drift between the stored total and the log).

**Archive**: no `archived`/`archived_at` concept exists on `strategies` today. Needs a new column (boolean or nullable timestamp — a timestamp doubles as "when," matching the `reservations.terminal_at` pattern already used elsewhere in this codebase for exactly this "null while live, set once terminal" shape). What "archived must block," concretely, given current code:
- **Webhook for an archived strategy**: `IngestSignal.ingest()` (`signals/application/ingest_signal.py:57-86`) does NOT look up the strategy at all today — it persists ANY `strategy_id` (parsed straight from `signal_type`) and enqueues a job unconditionally. Disabled-strategy skip happens much later, deep inside `AllocateCapital.allocate()` (`STRATEGY_DISABLED_SKIP_REASON`, `allocate_capital.py:104-110`), and only for the CONSUMES path. An archived strategy would need the same or an earlier guard — either at ingest (reject at the webhook, matching "refused" language) or reuse the disabled-skip point (silently skip, consistent with how disabled already works). This is a real design choice: refuse loudly at ingest (extra DB read on the hot 3-second path) vs. skip silently deep in allocation (consistent latency, but the webhook always returns 200/accepted even for a strategy the owner archived weeks ago, which may surprise the owner reading TradingView's alert log).
- **Enabling an archived strategy**: `UpdateStrategy.update()` has no such refusal today; must add one (raise a new `StrategyArchived`-type domain error, mapped to 409/422 at the router).
- **Listing**: `list_strategies()` (`strategies/infrastructure/router.py:170-173`) returns everything via `SqlAlchemyStrategyRepository(session).list_all()`; an archived strategy must be excluded (or filterable) so the Strategies view doesn't show it as active by default, while `/strategies/:uuid` detail + stats presumably still needs to load an archived one (decision 1: "Archive, never delete").

### 4. Keys in the vault with purpose (decisions 7-8)

**The vault's one-active-per-exchange constraint is a hard, confirmed blocker for storing two keys per exchange simultaneously.** Migration `0010_exchange_credentials.py:72-78` creates `ux_exchange_credentials_one_active_per_exchange`, `UNIQUE(exchange) WHERE is_active` — literally at most one active row per exchange, full stop, no purpose dimension. `SqlAlchemyCredentialVault.load(exchange)` (`accounts/infrastructure/credential_vault.py:49-67`) and `.store()` (`credential_vault.py:85-116`) both key by `exchange` alone. Migration `0013` (`0013_credential_rotation.py`) already removed a second constraint that would have collided with rotation, and its own docstring establishes the precedent this task needs to extend: add a `purpose` (`READ`/`TRADE`) column and change the partial unique index to `UNIQUE(exchange, purpose) WHERE is_active`; `load`/`store`/`hints` all gain a `purpose` parameter.

**Current call-site reality is more tangled than the owner's "two keys" framing suggests, and needs to be corrected during design, not assumed**: grepped every `.load(` call in `backend/src` — Bybit's vault credential is loaded via `.load(BYBIT_EXCHANGE)` at **six** call sites in `main.py` (lines 742, 808, 919, 1024, 1098, plus `_vault_credential` at 483) and is reused for BOTH `trade_client(...)` (opening orders, `exchange_for`) AND `read_only_client(...)` (balance sync, balance refresh, venue-position reads, reconciliation scan, booking prepare) — i.e., **Bybit today has only ONE key in the vault, used for both purposes**, contradicting CLAUDE.md's "two keys, not interchangeable" framing which is specifically about the read-only `.env` key vs. the trade vault key (that framing is accurate for a diagnostic/probe context, per `scripts/probe_credentials.py`, but the *production worker* code path for Bybit signs every read with the trade credential). `settings.bybit_api_key`/`bybit_api_secret` (`shared/config.py:117-118`) are defined but grepped with zero production call sites outside `bybit/factory.py` (needs a closer look at design time — likely only a fallback/default path or used by standalone scripts) — worth confirming they're truly dead before deciding what ".env stops holding keys" removes. Binance, in contrast, genuinely has a working two-source split today: the trade key comes from the vault (`binance_trade_client(...)` inside `exchange_for`, using `_vault_credential(vault, BINANCE_EXCHANGE)`), while the read-only key comes straight from `.env` via `binance_credentials_from_settings(settings)` (used ~5 times across balance sync, refresh, venue-position reads, reconciliation scan/prepare).

**Master key requirement is ALREADY true under DRY_RUN, not a new requirement**: `cipher = EnvelopeCipher.from_base64(settings.master_encryption_key)` (`main.py:632`) is built unconditionally in `build_worker_runner`, outside the `if settings.dry_run` branch — so `MASTER_ENCRYPTION_KEY` is already mandatory at worker startup regardless of DRY_RUN today. Decision 7's "the worker then needs the master key even under DRY_RUN" is a correct description of the CURRENT state, not a change this feature introduces.

**Vault self-test** (`worker.py:216-244`, `_assert_sealed_credentials_open`): iterates `vault.hints()` and opens each by `exchange` at startup, refusing to start on `DecryptionFailed`. Adding `purpose` means `hints()` returns one row per `(exchange, purpose)` and the self-test loop is otherwise unchanged in shape — a mechanical update, not a redesign.

**Key validation on save (decision 8) — permission-introspection endpoints**: 
- **Binance — VERIFIED via web search**: `GET /sapi/v1/account/apiRestrictions` returns exactly the fields decision 8 needs: `enableReading`, `enableWithdrawals`, `enableInternalTransfer`, `enableMargin`, `enableFutures`, `ipRestrict`. Maps cleanly: refuse if `enableWithdrawals`; the read slot must have `enableFutures=false` (or simply must fail a live trade probe); the trade slot must have `enableFutures=true`. `enableInternalTransfer` is the separate "internal transfer, allowed" permission decision 8 carves out.
- **Bybit — PARTIALLY VERIFIED, flagged UNVERIFIED for the withdraw check specifically**: `GET /v5/user/query-api` (Bybit's official "Get API Key Information" endpoint) exists and returns a `permissions` object with per-category arrays (`ContractTrade`, `Spot`, `Wallet`, etc. — `Wallet` carries `AccountTransfer`, matching CLAUDE.md's existing note that Bybit's internal-transfer permission is called `AccountTransfer`). What the web search did NOT confirm is whether this endpoint's response exposes a distinct "withdraw" flag the same way Binance's `enableWithdrawals` does, or whether Bybit governs withdrawal through a separately-managed withdrawal-address allowlist outside the key-permission object entirely (which is how Bybit withdrawal security is commonly described). **This must be confirmed with a live probe against the actual key before design finalizes the refusal logic** — same pattern the `book-venue-closes` exploration used for its unit 2a (verify the exact response shape live rather than trust docs, since this codebase has already been burned twice by Pionex docs disagreeing with the live venue — see CLAUDE.md's "Where the futures docs are wrong" section).
- "A live read must succeed" (validation a) and "the read slot key must not be able to trade / trade slot must be able to trade futures" (validation c) both need a lightweight live call at save time — `read_only_client`/`trade_client` factories already exist per exchange and could be reused for a one-off validation call, but nothing today calls them outside the worker's job handlers; a Settings-save endpoint would be the first caller from the API process itself rather than the worker.

### 5. Serving

**No static file serving exists today.** `create_app()` (`main.py:1261-1292`) only mounts `signals_router`, `strategies_router`, `reconciliation_router`, plus inline `/health`. No `StaticFiles` mount, no catch-all route. CORS (`main.py:1276-1282`) currently allows `settings.cors_origins`, which defaults to `["http://localhost:5173"]` (`shared/config.py:162`) — the Vite dev server only; would need the production origin added, or CORS becomes moot entirely if the SPA is served same-origin by this same FastAPI process (no cross-origin fetch to redact).

**Path collision, confirmed real**: `/strategies` is both the existing admin API prefix (`strategies/infrastructure/router.py:71-75`, `prefix="/strategies"`) AND the UI route family the owner wants (`/strategies/:uuid`, decision 2). A same-origin FastAPI static-file mount with an SPA fallback (serve `index.html` for any unmatched GET) would need either: (a) namespace the JSON API under `/api/...` (breaking change to the existing `/strategies`, `/reconciliation` admin surface — the frontend's own `apiFetch`/`API_BASE_URL` already abstracts the base path so updating callers is mechanical, but it's still a breaking API move); or (b) mount the SPA fallback ONLY for paths that are not already a registered API prefix (order routes so `/strategies` (no trailing path segment beyond what the API defines) and `/reconciliation`, `/health`, `/webhook/tradingview` are matched first, everything else falls through to `index.html`) — fragile as new API routes are added later, since forgetting to reserve a new prefix silently serves `index.html` for it instead of 404. `/webhook/tradingview` and `/health` do NOT collide with any SPA path under either option.

**A genuinely available third option, found while reading the frontend**: the existing App shell uses HASH navigation (`#dashboard`, `#strategies`, decision-noted in `app/App.tsx:17-22`: "No router library is added for a four-view shell (design.md § 12) -- the existing href=\"#...\" anchors drive this seed/update instead"). Hash fragments (`#/strategies/{uuid}`) never reach the server at all — the browser does not send them in the request line — so a hash-based `/strategies/:uuid`-equivalent route sidesteps the SPA-fallback/API-collision problem ENTIRELY: FastAPI only ever needs to serve `index.html` for `GET /` (or any non-API path, trivially, since there would be none) and mount `/assets/*`. This trades a URL that looks like `#/strategies/{uuid}` instead of a "real" `/strategies/{uuid}` path (no server-side deep-linking without a redirect shim, no path shown as `/strategies/{uuid}` in share links) for zero backend routing complexity and zero breaking change to the existing admin API. This is a genuine design-phase choice, not resolved here.

**Deployment topology (list only, per instruction not to design it)** — per decision 5 and CLAUDE.md's external-constraints section: Cloudflare Tunnel + Cloudflare Access in front of `strategymanager.trade` for the panel + admin API; DuckDNS + its existing proxy continues forwarding ONLY `/webhook/tradingview` (TradingView's IP allowlist and 3-second timeout are unrelated to Cloudflare and must keep working unchanged). What changes is infra config, not code: (1) a new Cloudflare Tunnel ingress rule routing `strategymanager.trade` to this FastAPI process; (2) Cloudflare Access policy gating who reaches that origin (separate from / in addition to the existing bearer-token `ADMIN_API_TOKEN` check, which stays as defense in depth); (3) `cors_origins` gains the production origin if the SPA is NOT served same-origin, or CORS becomes unnecessary if it is; (4) the DuckDNS proxy config is untouched (still webhook-only). None of this is application code.

### 6. Frontend

**No routing library installed** — `frontend/package.json` dependencies confirmed: `@tanstack/react-query`, `zustand`, `react-i18next`, `recharts`, `tailwind-merge`, `clsx`; no `react-router-dom` or equivalent. `App.tsx` drives everything off `window.location.hash` with a `NavKey` union (`dashboard | strategies | settings | bookings`) and a `hashchange` listener — a small, self-contained pattern, not a library. Adding `/strategies/:uuid` as a REAL path route (decision 2's literal wording) requires EITHER adopting a router library (react-router, most likely, given React 19 + Vite 6 + TS strict is the existing stack) and building the FastAPI SPA-fallback machinery from point 5, OR keeping the existing hash pattern and expressing `/strategies/:uuid` as `#/strategies/{uuid}` (extending `NavKey`-style parsing to carry a param) — see point 5's third option. This is the single biggest either/or in the whole change and touches both frontend and backend serving, so it should be decided once, together, at design time.

**Existing shared pieces immediately reusable**: `shared/api/client.ts`'s `apiFetch<T>` (bearer token injection, typed `ApiError`, 401-clears-token) is a clean base for every new endpoint's client wrapper — no changes needed to it, just new typed call functions per endpoint. `shared/auth/TokenGate.tsx` + `token-store.ts` already gate `BookingsListView` behind the paste-once admin token; the same gate wraps whatever new views are added. `shared/i18n/index.ts` (EN/ES via `react-i18next`) and `index.css`'s `@theme` tokens (`surface-*`, `ink-*`, `accent`, `profit`/`loss`/`idle`, `--font-mono` for tabular figures) are already the palette a PnL dashboard needs (green/red for profit/loss, `idle` amber already used for the DRY_RUN badge in `App.tsx:71-73`). TanStack Query is installed but not yet used anywhere in the codebase outside its dependency declaration — this change would be its first real consumer.

**Charts**: confirmed via the facts note (not re-verified here, file lives outside this repo at `D:/Code/RSI Divergence Strategy/informe/seleccion-de-pares.html`) — dependency-free inline SVG: log-scale equity line + drawdown area below, and a month×year "texture" grid using CSS `color-mix` saturation per cell on a fixed ±15% scale. `recharts` is already a frontend dependency but unused; reusing the report's own inline-SVG approach avoids introducing a second charting paradigm (recharts vs. hand-rolled SVG) into one dashboard — worth deciding explicitly whether recharts gets used at all, or the dependency-free approach wins throughout for consistency with the reference report the owner explicitly asked to match.

- **Strategies**: list/detail/create/edit already exist (`strategies_router`) and need no new backend work beyond the archive/allowed-pairs/enable-log additions above; stats (PnL, uptime, trade count, by-pair) are new reads per points 1 and 3; "copy-ready webhook message" is a pure frontend string template (the alert JSON shape from `signals/domain/alert.py`'s docstring, with the strategy's own `id` substituted) — no backend endpoint needed for it at all.
- **Settings**: list keys per exchange with last-4 + permissions — `CredentialVaultPort.hints()` already returns `last4`; permissions is new (needs point 4's live probe result cached somewhere, or queried on demand). Add/rotate with validation is new (point 4).

### Risks

- The vault `purpose` migration touches SIX call sites in `main.py` plus `worker.py`'s self-test plus every script under `scripts/store_*_credentials.py` — a mechanical but wide-reaching change; get the exact shape (enum vs text CHECK, column name) right once rather than migrating twice.
- Bybit's current single-key-for-both-purposes reality means "add a second Bybit key" is not additive — it changes which key signs which call at SIX existing production call sites, each of which currently works and is live-verified (per CLAUDE.md's round-trip note). This needs care, not just a schema add.
- The append-only ledger (rule 6) has no compensating-entry concept — if a future PnL bug misattributes a fill to the wrong allocation, there is no correction mechanism today (same risk already flagged in the `book-venue-closes` exploration's Q4/Q6, unresolved there too — worth knowing this is a standing gap, not new to this change).
- The path-collision / routing decision (points 5+6) is the one place a wrong early choice is expensive to reverse (breaking the existing `/strategies` API prefix, or committing to a router library + SPA fallback, are both significant enough to want decided once at design time, not discovered mid-implementation).
- Bybit's withdraw-permission introspection is UNVERIFIED; validation (b) in decision 8 cannot be implemented correctly without a live probe first.

### Rough PR slicing, risk-ordered (backend foundations -> API -> infra/serving -> frontend)

1. **Backend foundations, no API surface yet**: vault `purpose` migration + call-site rewiring (Bybit two-key split, Binance key relocated into vault); strategy `allowed_pairs` storage + `process_signal.py` refusal; strategy `archived_at` + enable/disable event log + archive guards in `UpdateStrategy`/webhook path. Each is independently testable against existing test suites and carries the highest blast-radius risk (touches money-moving code paths), so it goes first and alone.
2. **New read models**: per-allocation realized PnL, per-pair stats, cumulative uptime query, pool-balance-at-request-time is explicitly NOT built (point 1's caveat) — pure additions, no behavior change to existing paths.
3. **API surface**: new Overview/Strategies-stats/Settings-keys routers, all behind `require_admin_token`, composing the read models from step 2 and existing `strategies_router`/`reconciliation_router` data.
4. **Serving/infra**: the routing decision from points 5+6 (hash vs. path + SPA fallback + `/api` prefix decision), static file mount, CORS/production-origin config, Cloudflare Tunnel ingress rule (infra, not code, but sequenced here since the frontend build target depends on it).
5. **Frontend**: shell/nav changes for the chosen routing approach, then Overview, Strategies, Settings views layered on top of steps 3-4, using the frontend-design plugin per the standing constraint.

### Questions that are genuinely the OWNER's (product), separate from design

1. Refuse-at-webhook vs. skip-silently-in-allocation for an archived strategy's signal (point 3) — a UX/product call about whether the owner wants to SEE a refusal in the webhook response/log for an archived strategy, or have it behave exactly like disabled (silent skip).
2. Array column vs. child table for allowed pairs (point 2) is technically a design decision, but has a product-visible consequence: a child table makes "per-pair settings later" cheap, an array does not — worth the owner knowing this trade-off exists even though the choice itself belongs to design.
3. Whether the % return curve compounds multiplicatively per trade or is shown as a flat list with a separately-computed running total (point 1) — changes what the drawdown/monthly-grid numbers actually mean, and the owner referenced a specific report as the model to match, so the report's own convention (if inspectable) may already answer this.
4. `/strategies/:uuid` as a real path vs. a hash route (points 5+6) — the owner's decision doc says "Routes like `/strategies/:uuid`" but that phrasing doesn't distinguish hash-based from path-based; worth confirming intent before committing to either the router-library + SPA-fallback path or the hash-route path, since they carry meaningfully different implementation cost and reversibility.
